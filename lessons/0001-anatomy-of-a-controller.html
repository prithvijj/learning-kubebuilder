Lesson 1 · Kubebuilder & Controller Internals

The Anatomy of a Controller

You already know what happens when kubectl apply hits a built-in type: the API server validates it and writes it to etcd. That's the whole story for a Pod object sitting there. It's also, perhaps surprisingly, the entire story for a Custom Resource too — right up until something else decides to care about it.

Key idea: a CRD + a CR, by themselves, do nothing. A CRD just teaches the API server a new schema. A CR is just an object of that schema, sitting in etcd. No logic runs because you created one. Logic only runs because a separate process — a controller — is watching and decided to react.

What actually lands in your function

This is the detail that reshapes how you write Reconcile: the workqueue holds keys — a namespace and a name — not events, not diffs, not object bodies. If the same object changes three times before a worker gets to it, that's still one key in the queue. Your function gets called once, and has to re-derive the full current state from scratch.

This is why controllers must be level-triggered, not edge-triggered. Your Reconcile function can't assume it knows what happened. It has to look at the object as it is right now and decide what, if anything, needs to change — every single time it's called, including on a plain periodic resync where nothing changed at all.

  2. You run kubectl apply -f my-cr.yaml
  3. A worker pops the key and calls your Reconcile function
  4. The API server validates the object and stores it in etcd
  5. The controller’s informer gets a watch event and updates its local cache
