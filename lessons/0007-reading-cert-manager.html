Lesson 7 · Kubebuilder & Controller Internals

Reading cert-manager

Everything so far has been a toy CRD you built yourself. This lesson is different: no code to write, just real production source to read, using the vocabulary from Lessons 1–6 as your map. cert-manager issues and renews TLS certificates cluster-wide — it's one of the most widely deployed operators in the ecosystem, so if you work with Kubernetes long enough, you'll likely meet it again.

Step 0 — orient yourself

Open these two, side by side with your own project:

  • pkg/apis/certmanager/v1/types_certificate.go — the Certificate CRD's Go type, the direct counterpart to your api/v1/greeting_types.go.
  • pkg/controller/certificates/ — where the reconciling logic lives, the counterpart to your internal/controller/greeting_controller.go.

Look inside that second directory. You'll find trigger/, keymanager/, requestmanager/, issuing/, readiness/, revisionmanager/ — six separate controllers, all watching the same Certificate object.

New idea this lesson introduces: your Greeting controller does everything in one Reconcile — validate, sync a ConfigMap, set status, handle deletion. cert-manager splits one CRD's entire lifecycle across six narrow controllers instead of one large one. Each owns exactly one job and (typically) one status condition. None of them call each other directly — they coordinate purely by writing to the shared Certificate object's status, the same way your finalizer logic and your Owns() watch never call each other directly either.

Step 1 — read one controller closely

Open trigger_controller.go. Its whole job is deciding whether a certificate needs to be reissued — not doing the reissuing itself. Find these three things (use Ctrl-F, don't just skim):

  • The function that gets called per-object. What is it named, and what does it take as a parameter — is it Reconcile(ctx, req)?
  • The status condition type it sets when reissuance is needed.
  • A check involving the target Secret's owner — what problem is it guarding against?

What you should find: the function is ProcessItem(ctx context.Context, key types.NamespacedName) error — not Reconcile(ctx, req). cert-manager built its own controller/workqueue plumbing directly on client-go, predating widespread controller-runtime adoption. The name and signature are different. The contract is identical: take a key, re-fetch full current state, decide, return an error or don't. This is Lesson 1's level-triggered pattern again, wearing different clothes. When it decides reissuance is needed, it sets an "Issuing" condition to True — and the Secret-ownership check exists to stop two different Certificates from fighting over control of the same target Secret.

Step 2 — a real finalizer, not a toy one

Now look at pkg/controller/acmechallenges/sync.go. A Challenge object represents cert-manager proving domain ownership to a Certificate Authority — by creating a real DNS TXT record or a temporary HTTP route. Search for Finalizer.

You'll find cmacme.ACMEDomainQualifiedFinalizer, and a finalize() function that calls solver.CleanUp() — which removes the actual DNS record or HTTP route from a real external provider before the finalizer comes off and the Challenge is allowed to disappear. Your Lesson 6 farewell log file was a stand-in for exactly this class of problem: an external side effect Kubernetes' own garbage collector could never know how to reverse.

Step 3 — one more contrast worth noticing

Check CertificateStatus in types_certificate.go from Step 0. Its Conditions field is typed []CertificateCondition — a type cert-manager defined itself — not []metav1.Condition like your GreetingStatus.

metav1.Condition became a shared community standard after cert-manager had already built its own equivalent shape (Type, Status, Reason, Message, LastTransitionTime). This is a normal artifact of a project's age, not a mistake — expect to see this kind of "almost-standard, predates the standard" shape often once you start reading enough real operators.

Check your understanding

trigger_controller.go's per-object entrypoint is ProcessItem(ctx, key), not Reconcile(ctx, req). What does this tell you?

Primary source Everything in this lesson is the cert-manager source itself — github.com/cert-manager/cert-manager. For the user-facing side of what these controllers implement, cert-manager.io's Certificate docs are the high-trust reference.
