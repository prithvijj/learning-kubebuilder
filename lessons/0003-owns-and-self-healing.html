Owns() and Self-Healing

Your controller from Lesson 2 watches exactly one thing: Greeting. It has no idea the ConfigMap it created even exists once Reconcile returns. Let's prove that's a gap, then close it with one line.

Step 0 — prove the gap exists

With make run still going from Lesson 2, in another terminal:

kubectl patch configmap greeting-sample --type merge -p '{"data":{"message":"hand-edited, not from spec"}}'
kubectl get configmap greeting-sample -o yaml

Nothing happens. No new log line, no correction. The edit sticks forever, even though it directly contradicts the Greeting's spec.message. Your controller is blind to this object outside of the one moment it created or last touched it.

Step 1 — notice what's already in place

Look back at your Lesson 2 Reconcile code — specifically this line, which you already wrote: 

return controllerutil.SetControllerReference(&greeting, cm, r.Scheme)

Check what it actually did:

kubectl get configmap greeting-sample -o yaml

Look for metadata.ownerReferences. There's already a record pointing from the ConfigMap back to the Greeting, with controller: true. You built the mechanism a secondary watch needs before you had the watch itself.

Step 2 — add the watch

In internal/controller/greeting_controller.go, find SetupWithManager:

func (r *GreetingReconciler) SetupWithManager(mgr ctrl.Manager) error {
	return ctrl.NewControllerManagedBy(mgr).
		For(&appsv1.Greeting{}).
		Named("greeting").
		Complete(r)
}

Add one line:

func (r *GreetingReconciler) SetupWithManager(mgr ctrl.Manager) error {
	return ctrl.NewControllerManagedBy(mgr).
		For(&appsv1.Greeting{}).
		Owns(&corev1.ConfigMap{}).
		Named("greeting").
		Complete(r)
}

What that line actually does: Owns() wires up a second watch — this time on ConfigMaps — using an event handler called EnqueueRequestForOwner. When a ConfigMap changes, that handler reads its owner reference, finds the Greeting it points at, and enqueues the Greeting's namespace/name into the exact same WorkQueue from Lesson 1. Your Reconcile function is called no differently than before — it still has no idea whether it woke up because the Greeting changed or because someone poked its ConfigMap. It just re-derives desired state, same as always.

No RBAC change needed — Lesson 2's marker already grants watch on ConfigMaps. Restart the manager:

# Ctrl-C the running make run, then:
make run

Step 3 — watch it heal

Repeat the hand-edit from Step 0:

kubectl patch configmap greeting-sample --type merge -p '{"data":{"message":"hand-edited, not from spec"}}'

This time a log line should appear immediately — Reconcile fired without you touching the Greeting at all. Check the ConfigMap again: 

kubectl get configmap greeting-sample -o yaml

It's back to matching spec.message. Nothing in your code branches on "was this triggered by a hand-edit" — it's the same CreateOrUpdate call from Lesson 2, just triggered from a different source.

Step 4 — the trap: delete the ConfigMap

kubectl delete configmap greeting-sample

Watch the logs: a delete event fires the same Reconcile, which calls CreateOrUpdate again and recreates the ConfigMap from scratch. Self-healing in both directions — drift and disappearance.

Step 5 — the other trap: delete the Greeting

kubectl delete greeting greeting-sample
kubectl get configmap greeting-sample

The ConfigMap disappears too. Before you conclude "my Owns() watch did that" — check your manager's logs. There's no Reconcile log line for it, because there's nothing to reconcile: the Greeting is gone, so r.Get returns not-found and the function returns early.

Something else deleted it: Kubernetes' own garbage collector, a built-in control loop that has nothing to do with your code. It watches owner references cluster-wide and deletes an object once every owner pointing at it is gone. The same field (metadata.ownerReferences, controller: true) drives two independent systems — your Owns() watch, and the cluster's garbage collector. Worth keeping distinct: one runs your Go code, the other never does.

Primary source controller-runtime's Builder.Owns docs for the exact mechanics (including OnlyControllerOwner vs. watching every owner). For the garbage collector side, see the Kubernetes docs on owners and dependents.
