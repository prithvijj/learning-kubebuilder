Finalizers and Custom Cleanup

Lesson 3's garbage collector deletes your ConfigMap automatically when the Greeting goes, because the ConfigMap lives in the API server and has an owner reference. But GC has zero visibility into anything outside Kubernetes — a cloud load balancer, a row in an external database, a webhook call to some other system. If your controller ever needs to clean up something like that before the object disappears, GC can't help. This is what finalizers are for.

The mechanism, in one sentence: a finalizer is a string on the object that tells the API server "don't actually delete this from etcd yet." kubectl delete sets metadata.deletionTimestamp instead of removing the object — this is what shows up as Terminating — and your Reconcile keeps getting called until every finalizer is gone.

Step 0 — make sure you have a live Greeting

kubectl apply -f config/samples/apps_v1_greeting.yaml
kubectl get greeting

Step 1 — add a finalizer to the type

In greeting_controller.go, add a constant near the top:

const greetingFinalizer = "apps.kubebuilder-lessons.dev/finalizer"

Add these imports:

"os"
"time"

Step 2 — branch on DeletionTimestamp

Right after the initial r.Get in Reconcile (before the empty-message check), add: 

if !greeting.DeletionTimestamp.IsZero() {
	if controllerutil.ContainsFinalizer(&greeting, greetingFinalizer) {
		if err := r.cleanupExternalResource(&greeting); err != nil {
			return ctrl.Result{}, err
		}
		controllerutil.RemoveFinalizer(&greeting, greetingFinalizer)
		if err := r.Update(ctx, &greeting); err != nil {
			return ctrl.Result{}, err
		}
	}
	return ctrl.Result{}, nil
}

if controllerutil.AddFinalizer(&greeting, greetingFinalizer) {
	if err := r.Update(ctx, &greeting); err != nil {
		return ctrl.Result{}, err
	}
	return ctrl.Result{}, nil
}

Both branches call r.Update, not r.Status().Update() — metadata.finalizers is ordinary object metadata, not status. This is the mirror image of the mistake Lesson 4 warned about: use the wrong one here and the finalizer never persists, and you'd have a Greeting stuck in Terminating with no obvious reason why.

Returning right after adding the finalizer looks like it does nothing useful, but it isn't wasted: that r.Update call is itself a change the informer will see, which enqueues this exact key again — the next Reconcile picks up from a fresh r.Get with the finalizer already in place. Same level-triggered logic from Lesson 1, just triggered by your own write this time.

Step 3 — the cleanup itself

Add this method below Reconcile:

func (r *GreetingReconciler) cleanupExternalResource(greeting *appsv1.Greeting) error {
	line := fmt.Sprintf("%s: goodbye from %s/%s (message was %q)\n",
		time.Now().Format(time.RFC3339), greeting.Namespace, greeting.Name, greeting.Spec.Message)
	f, err := os.OpenFile("/tmp/greeting-farewells.log", os.O_APPEND|os.O_CREATE|os.O_WRONLY, 0644)
	if err != nil {
		return err
	}
	defer f.Close()
	_, err = f.WriteString(line)
	return err
}

A file on disk is standing in for "something Kubernetes cannot see or clean up on its own" — in a real controller this would be a cloud API call, a DNS record deletion, anything external.

Restart the manager: make run. Then confirm the finalizer landed on your existing Greeting, without you re-applying anything:

kubectl get greeting greeting-sample -o jsonpath='{.metadata.finalizers}'

That happened because the manager re-lists everything into its cache on startup, which queues a Reconcile for every existing object — not just future changes.

Step 4 — watch a clean deletion

To actually see the Terminating window (cleanup is normally too fast to catch), temporarily add a slow-down at the top of cleanupExternalResource:

time.Sleep(5 * time.Second) // temporary, for observing Terminating — remove after this step

Restart make run, then in another terminal:

kubectl delete greeting greeting-sample &
sleep 1
kubectl get greeting greeting-sample -o yaml | grep -A2 deletionTimestamp

You should see deletionTimestamp set while the object is still there. Wait for the delete to finish, then check the proof of cleanup:

cat /tmp/greeting-farewells.log

Now remove the time.Sleep line — it was only for this observation.

Step 5 — the failure mode everyone eventually hits

Re-apply the sample, then comment out just the finalizer-removal half of the deletion branch:

if controllerutil.ContainsFinalizer(&greeting, greetingFinalizer) {
	if err := r.cleanupExternalResource(&greeting); err != nil {
		return ctrl.Result{}, err
	}
	// controllerutil.RemoveFinalizer(&greeting, greetingFinalizer)
	// if err := r.Update(ctx, &greeting); err != nil {
	// 	return ctrl.Result{}, err
	// }
}

Restart make run, then:

kubectl delete greeting greeting-sample

It hangs. Forever. Ctrl-C it, and confirm the object is still there, permanently Terminating: 

kubectl get greeting greeting-sample

This is the real-world "why won't my resource delete" problem — almost everyone who's used Kubernetes for a while has hit a stuck namespace or CRD for exactly this reason: a finalizer that never gets removed, usually because the controller that owns it crashed, was uninstalled, or (like here) has a bug. The escape hatch, when you're sure it's safe: 

kubectl patch greeting greeting-sample -p '{"metadata":{"finalizers":[]}}' --type=merge

This forces the finalizer list empty directly, so the API server completes the delete — but your cleanup code never ran. Only reach for this once you know that's an acceptable outcome.

Uncomment the RemoveFinalizer/Update lines from Step 5, restart make run, and re-apply the sample to leave your controller in its correct, working state.

Primary source Kubernetes docs — Finalizers for the concept itself, and controllerutil docs for the exact helper signatures used above.
