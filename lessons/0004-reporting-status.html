Lesson 4 · Kubebuilder & Controller Internals

Reporting Status with Conditions

Everything so far has been invisible from kubectl get. Try it: 

kubectl get greeting

Just a name and an age. Your controller knows exactly what it did — it logs it — but nothing about that knowledge reaches the object itself. This lesson closes that gap using the same mechanism nearly every real CRD uses: status conditions.

Step 0 — you already have the plumbing

Open api/v1/greeting_types.go. Two things are already there, scaffolded by default:

// +kubebuilder:object:root=true
// +kubebuilder:subresource:status

// Greeting is the Schema for the greetings API
type Greeting struct {
	...
}
type GreetingStatus struct {
	// +listType=map
	// +listMapKey=type
	// +optional
	Conditions []metav1.Condition `json:"conditions,omitempty"`
}

And in greeting_controller.go, the RBAC markers already grant you what you need: 

// +kubebuilder:rbac:groups=apps.kubebuilder-lessons.dev,resources=greetings/status,verbs=get;update;patch

greetings/status is a distinct resource as far as RBAC and the API server are concerned — a separate status subresource, not just a field on the main object.

The pitfall this causes: because +kubebuilder:subresource:status is set, a plain r.Update(ctx, &greeting) will silently not persist any change you made to greeting.Status. You must call r.Status().Update(ctx, &greeting) for status changes specifically. Mixing these up is one of the most common first-operator bugs — the code compiles, runs, logs success, and the status just never appears.

Step 1 — set a condition

Add these imports to greeting_controller.go: 

import (
	"fmt"

	"k8s.io/apimachinery/pkg/api/meta"
)

Then, right after the r.Get call in Reconcile — before you build the ConfigMap — add a guard for an empty message: 

if greeting.Spec.Message == "" {
	meta.SetStatusCondition(&greeting.Status.Conditions, metav1.Condition{
		Type:    "Ready",
		Status:  metav1.ConditionFalse,
		Reason:  "EmptyMessage",
		Message: "spec.message must not be empty",
	})
	if err := r.Status().Update(ctx, &greeting); err != nil {
		return ctrl.Result{}, err
	}
	return ctrl.Result{}, nil
}

And after the CreateOrUpdate call succeeds, replace the final log.Info / return with:

meta.SetStatusCondition(&greeting.Status.Conditions, metav1.Condition{
	Type:    "Ready",
	Status:  metav1.ConditionTrue,
	Reason:  "ConfigMapSynced",
	Message: fmt.Sprintf("configmap %s is in sync", cm.Name),
})
if err := r.Status().Update(ctx, &greeting); err != nil {
	return ctrl.Result{}, err
}

log.Info("reconciled greeting", "configmap-op", op)
return ctrl.Result{}, nil

meta.SetStatusCondition (from k8s.io/apimachinery/pkg/api/meta) handles the fiddly part — it sets LastTransitionTime for you, only bumping it when the Status value actually flips, and updates an existing condition of the same Type in place instead of appending a duplicate. It does not set ObservedGeneration — that's on you if you need it, and you'll want it once you start caring whether status reflects the latest spec or a stale one.

Step 2 — make it visible in kubectl get

Add these markers directly above the Greeting struct, alongside the ones already there:

// +kubebuilder:printcolumn:name="Ready",type="string",JSONPath=".status.conditions[?(@.type=='Ready')].status"
// +kubebuilder:printcolumn:name="Reason",type="string",JSONPath=".status.conditions[?(@.type=='Ready')].reason"
// +kubebuilder:object:root=true
// +kubebuilder:subresource:status

Regenerate and reinstall the CRD, then restart the manager:

make manifests generate
make install
# Ctrl-C the running make run, then:
make run

Step 3 — watch both branches

kubectl patch greeting greeting-sample --type merge -p '{"spec":{"message":""}}'
kubectl get greeting

You should see Ready=False, Reason=EmptyMessage. Now fix it:

kubectl patch greeting greeting-sample --type merge -p '{"spec":{"message":"back to normal"}}'
kubectl get greeting

Ready flips to True, Reason to ConfigMapSynced — a real, useful kubectl get, driven by the same Reconcile function, no new watch, no new mechanism.

Where this goes next

That closes all four success criteria from your mission at least once: you can explain the machinery, you built a CRD + controller from scratch, you made it self-healing, and it now reports status the way real operators do. From here, two good directions: writing an automated test for Reconcile with envtest (so you're not hand-testing with kubectl patch every time), or picking a real open-source operator and reading its controller with this vocabulary in hand.
